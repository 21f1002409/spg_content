Agile Methodology, Scrum Roles & Sprint Velocity Tricks

Scrum Master, Product Owner, Daily Standup 3 Qs, Retrospective & Velocity Math

Summary: Deep dive into Scrum framework roles, ceremonies, and numerical velocity calculations seen in recent PYQs.
Core Topic

1. Scrum Framework Roles & Ceremonies

Scrum Master: Enforces Scrum rules, removes impediments, ensures time-boxed meetings, acts as a coach (does NOT assign tasks or manage backlog priorities).

Product Owner: Owns the Product Backlog, prioritizes stories based on ROI and customer value.

Development Team: Cross-functional, self-organizing group delivering working software increments.

Daily Scrum / Standup: 15-minute time-boxed daily meeting where every member answers 3 exact questions: 1) What did I complete yesterday? 2) What will I work on today? 3) What impediments/blockers are in my way?

⚡ PYQ SECRET EXAM TRICK

Scrum Role Confusion Trap

"Never confuse Product Owner and Scrum Master duties in exam questions!"

Exam Scenario: If question asks "Who notes missing time-boxes or process breaches?", answer is Scrum Master. If question asks "Who prioritizes backlog for business value?", answer is Product Owner.
💡 MNEMONIC: PO = WHAT & VALUE | SM = HOW & PROCESS
Core Topic

2. Sprint Retrospective vs Sprint Review

Sprint Review: Focuses on the PRODUCT. Team demonstrates the working increment to stakeholders.

Sprint Retrospective: Focuses on the PROCESS & TEAM DYNAMICS. Team evaluates what went well, what failed in collaboration, and how to improve next sprint.

Core Topic

3. Sprint Velocity Calculation Formula & PYQ Trick

Velocity = Sum of story points for all COMPLETELY FINISHED user stories in a sprint.

CRITICAL EXAM RULE: Partially completed user stories contribute ZERO points to velocity! (e.g., 5 story points task that is 90% done = 0 points).

// Sprint Velocity Calculation Example
// PYQ Problem: Sprint 1 completed: Task A (3 pts, 100%), Task B (5 pts, 100%), Task C (8 pts, 80% done).
// Calculate Velocity:
const taskA = 3; // Finished
const taskB = 5; // Finished
const taskC = 0; // NOT 100% finished! Contributes 0!

const sprintVelocity = taskA + taskB + taskC; // Velocity = 8 story points!
Analysis: Only stories marked as 100% DONE according to Definition of Done count toward Velocity.

Functional vs Non-Functional Requirements Cheat Sheet

SOLID Design Principles Master Guide & PYQ Code Recognition

SRP, OCP, LSP, ISP & DIP Code Examples, Violation Detection & Fixes

Summary: Deep dive into SOLID principles with real code snippets taken directly from exam question sets.
Core Topic

1. SRP (Single Responsibility Principle)

A class should have ONE and only one reason to change.

Violation PYQ Example: An `Employee` class that calculates salary, renders HTML representation, AND saves employee records directly to MySQL database.

Core Topic

2. OCP (Open-Closed Principle)

Software entities should be OPEN for extension, but CLOSED for modification.

Violation PYQ Example: A `SmartDeviceController` containing a giant `switch(deviceType)` block. Adding a new `AC` or `Fan` requires modifying existing switch statements.

// OCP Compliant Refactoring (Strategy / Interface pattern)
interface Switchable {
  turnOn(): void;
  turnOff(): void;
}

class LightBulb implements Switchable {
  turnOn() { console.log("Bulb Glowing"); }
  turnOff() { console.log("Bulb Off"); }
}

class AirConditioner implements Switchable {
  turnOn() { console.log("AC Cooling"); }
  turnOff() { console.log("AC Off"); }
}

// DeviceManager is CLOSED for modification, OPEN for new Switchable devices!
class SmartDeviceManager {
  operate(device: Switchable) {
    device.turnOn();
  }
}
Analysis: Adding new devices requires zero changes inside SmartDeviceManager class.
Core Topic

3. LSP (Liskov Substitution Principle)

Subtypes must be completely substitutable for their base types without altering program correctness.

Violation PYQ Example: `Square` extending `Rectangle` where setting width alters height unexpectedly, or `Ostrich` extending `Bird` throwing `FlyNotSupportedException`.

Core Topic

4. ISP (Interface Segregation Principle)

Clients should not be forced to depend upon interfaces/methods they do not use.

Violation PYQ Example: A fat interface `OrderProcessor` containing `processDigitalDownload()`, `packagePhysicalBox()`, and `shipViaFedEx()`. A `DigitalEbookProcessor` is forced to implement dummy `shipViaFedEx()` methods.

⚡ PYQ SECRET EXAM TRICK

SOLID Violation Cheat Sheet

"Identify SOLID violation in code snippet within 10 seconds:"

Exam Scenario: 1) Class doing DB + UI + Business logic ➔ SRP violation. 2) Giant if/else or switch checking object type ➔ OCP violation. 3) Child class throwing UnsupportedOperationException ➔ LSP violation. 4) Class forced to implement empty/dummy methods ➔ ISP violation. 5) High-level class instantiating concrete low-level class with "new" ➔ DIP violation.
💡 MNEMONIC: SRP=1 Job | OCP=No Switch | LSP=No Dummy Exceptions | ISP=Small Interfaces | DIP=Depend on Interfaces

"Determine cohesion type in 3 questions:"

Creational Design Patterns: Builder, Factory & Singleton

Solving Telescopic Constructor Explosion & Object Instantiation Scenarios

Summary: Master Creational patterns with direct focus on the Builder pattern explosion problem frequently tested in PYQs.
Core Topic

1. Builder Pattern & Telescopic Constructors

Problem: A class has many optional attributes (e.g., `Employee` with name, age, salary, address, phone, TA, HRA, bonus, PF, medicalAllowance). Constructing objects requires creating 10 overloaded constructors with combinations of null values (Telescopic Constructor anti-pattern).

Solution: Builder Pattern constructs complex objects step-by-step using a fluent method-chaining API.

// Builder Pattern Example (PYQ Scenario)
class Employee {
  private name: string;
  private salary: number;
  private hra?: number;
  private ta?: number;

  constructor(builder: EmployeeBuilder) {
    this.name = builder.name;
    this.salary = builder.salary;
    this.hra = builder.hra;
    this.ta = builder.ta;
  }
}

class EmployeeBuilder {
  name: string;
  salary: number;
  hra?: number;
  ta?: number;

  constructor(name: string, salary: number) {
    this.name = name;
    this.salary = salary;
  }

  setHRA(hra: number) { this.hra = hra; return this; }
  setTA(ta: number) { this.ta = ta; return this; }

  build(): Employee {
    return new Employee(this);
  }
}

// Usage avoiding telescopic constructor:
const emp = new EmployeeBuilder("Alex", 75000).setHRA(15000).build();
Analysis: Step-by-step construction of complex object without telescopic constructors.
⚡ PYQ SECRET EXAM TRICK

The "Telescopic Constructor" Trigger

"If exam question prompt mentions "too many optional parameters", "constructor explosion", or "building complex object step-by-step", answer is BUILDER PATTERN!"

Exam Scenario: PYQ: "An Applicant form has 15 optional fields causing constructor overload. Which pattern solves this?" ➔ Builder Pattern.
💡 MNEMONIC: MANY OPTIONAL PARAMS ➔ BUILDER PATTERN

Intent: Converts the interface of an existing class into another interface expected by clients. Allows incompatible classes to work together.

Core Topic

Intent: Provides a single simplified, high-level interface to a complex subsystem of multiple classes.

PYQ Scenario: `OrderService.placeOrder()` internally coordinating inventory lookup, payment processing, shipping label creation, and SMS dispatch.

Association: Solid line with arrow ──> (Simple relationship between classes).

Aggregation: Hollow diamond ──◇ (Weak "has-a" relationship; child can exist independently of parent, e.g., Department and Teacher).

Dependency: Dashed line arrow - - -> (Uses temporary parameter method dependence).

COCOMO Model Effort & Cost Formulas

Organic, Semi-Detached & Embedded Modes, EAF Multipliers & Person-Months (PM) Math

Summary: Master COCOMO software cost estimation formulas, coefficients, and step-by-step exam calculations.
Core Topic

1. COCOMO Model Modes & Coefficients

COCOMO (Constructive Cost Model) estimates Effort (Person-Months) based on thousands of delivered lines of code (KLOC).

Project ModeTeam & Project CharacteristicsCoeff `a`Exponent `b`Basic Effort Formula
Organic ModeSmall team, familiar environment, well-understood flexible requirements2.41.05Effort = 2.4 × (KLOC)^1.05
Semi-DetachedMedium team, mixed experience, combination of rigid & flexible rules3.01.12Effort = 3.0 × (KLOC)^1.12
Embedded ModeComplex system, tight hardware/software constraints, strict compliance3.61.20Effort = 3.6 × (KLOC)^1.20
⚡ PYQ SECRET EXAM TRICK

COCOMO Coefficient Memory Mnemonic

"Remember `a` values: 2.4, 3.0, 3.6 (Increases by +0.6 each level!). Remember `b` values: 1.05, 1.12, 1.20."

Exam Scenario: Organic `a=2.4`, Semi `a=3.0`, Embedded `a=3.6`. Notice 2.4 + 0.6 = 3.0; 3.0 + 0.6 = 3.6!
💡 MNEMONIC: 2.4 ➔ 3.0 ➔ 3.6 (+0.6 STEP!)
Core Topic

2. Intermediate COCOMO & Cost Calculation

Nominal Effort = a × (KLOC)^b

Adjusted Effort (PM) = Nominal Effort × EAF (Effort Adjustment Factor from 15 cost drivers).

Total Project Cost = Adjusted Effort (Person-Months) × Monthly Salary per Developer.

Development Time (Tdev) = c × (Effort)^d (where c=2.5, d=0.38 for organic).

1. Cyclomatic Complexity Formulas

Formula 1 (Edges & Nodes): V(G) = E - N + 2P (where E = Edges, N = Nodes, P = Connected components = 1).

Formula 2 (Enclosed Regions): V(G) = R (where R = Number of enclosed regions in planar graph + 1 outer region).

Formula 3 (Predicate Nodes Shortcut - MOST IMPORTANT FOR EXAMS!): V(G) = P + 1 (where P = number of decision predicate conditions).

"Do NOT draw control flow graphs! Count number of conditional branch statements (`if`, `elif`, `while`, `for`, `case`, `&&`, `||`) and ADD 1!"

Debugging Strategies & Fault vs Error vs Failure

Terminology Distinction: Human Error ➔ Code Fault ➔ System Failure

Summary: Master the precise distinction between Fault, Error, and Failure, plus Blackbox vs Backwards debugging techniques.
Core Topic

1. Fault vs Error vs Failure Triad

Error (Human Mistake): A human programmer mistake while typing logic or design (e.g. developer writes `interest = principal * 0.5` instead of `0.05`).

Fault / Bug (Static Code Defect): The incorrect static code existing inside the codebase as a consequence of the error.

Failure (Observable Dynamic Behavior): The observable incorrect output, crash, or unexpected behavior during execution (e.g. bank customer receives 500% interest payout on screen).

⚡ PYQ SECRET EXAM TRICK

The Error-Fault-Failure Sequence

"Human makes ERROR ➔ Creates code FAULT ➔ Causes system FAILURE during execution!"

Exam Scenario: PYQ: "A developer mistypes variable name `val1` instead of `val2` in source file." ➔ Answer: Fault in code caused by human Error.
💡 MNEMONIC: HUMAN ERROR ➔ CODE FAULT ➔ SYSTEM FAILURE
Core Topic

2. Debugging Strategies Comparison

Forwards Debugging: Tracing execution flow from the initial triggering user event forward to the crash location.

Backwards Debugging: Starting at the observed crash point/error state and stepping backwards through call stack to find origin.

Blackbox Debugging: Debugging relying solely on inputs, outputs, logs, and API docs without inspecting internal source code.

Profiling: Using profiler tools to measure CPU cycle consumption, memory allocations, and performance bottlenecks.
